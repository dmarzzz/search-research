Searching & tagging your corpus — 2026 frontier

What's actually winning in text retrieval right now, what's been quietly displaced, and what to build for a corpus of tens of thousands. Local-first bias, papers and code, no marketing.

scope: ~30k docs types: transcripts · memos · slack budget: local-first compiled: —
your situation Tens of thousands of transcripts, internal memos, and slack messages. You want fast search, find-similar, and a multi-tier tag system without paying an LLM to read every doc. You've heard RAG is overkill — that's almost right, but the truth is more interesting: RAG didn't die, it just stopped being a pipeline and started being a tool inside an agent.

01The 2026 starter stack — by corpus size

Most "what should I use?" advice ignores the dominant variable: how big is your corpus? At 1k docs you can stuff everything into a single LLM call. At 100M docs you need real distributed infrastructure. In between, the recommendation changes step by step.

02Is RAG overkill?

Short answer: not for your scale. The 2023 RAG stack — chunk → embed → vector DB → top-k → rerank → stuff into LLM → synthesize — got reputation-killed because people used it for problems where simpler approaches worked. But for ~50M tokens of corpus, "just use long context" isn't an option.

03What replaced "the 2023 RAG stack"

then (2023)

chunk every doc into 512-token windows → embed with ada-002 → push to Pinecone → at query time: embed the query, top-k retrieve, rerank with Cohere, stuff into a GPT-4 prompt with a system message saying "answer based only on the context."

now (2026)

  1. Late chunking (arXiv:2409.04701) — embed the full doc through the transformer, then chunk after the token-level vectors are computed. Cross-chunk context is preserved. Now built into Jina v3.
  2. Long-context embedders — Cohere embed-v4 hits 128k token context; Voyage-3-large does 32k. Most full memos no longer need chunking.
  3. Hybrid by default — BM25 + dense fusion (reciprocal rank or RRF) is now table-stakes. Pure dense loses to hybrid on entity/acronym/exact-phrase queries.
  4. Agentic retrieval (arXiv:2501.09136) — the model decides when, how, and how often to search. 34→89% on multi-hop reasoning vs. static retrieval.
  5. Agent + tool, not pipeline — instead of `retrieve_then_answer()`, the LLM is given a `search()` tool and uses it iteratively. Anthropic and OpenAI both ship this pattern as default.

07Multi-tier tagging — the 3-phase plan

The current frontier consensus: don't try to LLM-tag every doc. Embed once, then layer cheap-to-expensive methods. Each phase increases cost and recall by ~10x.

phase 1
week 1 · ~50 labeled docs

Cluster & spot-check

  • BERTopic on all embeddings → 20–50 clusters
  • Read 3 docs per cluster, write a tag for the whole cluster
  • Surface outlier clusters first — the data shows you the taxonomy
→ rough taxonomy emerges from data, no labels needed
phase 2
weeks 2-3 · ~500 labeled docs

k-NN + active learning

  • Prototype networks — class as embedding centroid
  • modAL uncertainty + diversity sampling
  • Cleanlab v2.6 audit catches 10-30% mislabels
→ self-tagging working at ~85% accuracy
phase 3
week 4+ · ~3k labeled docs

LLM fallback & hierarchy

  • Hierarchical contrastive loss for the 3-tier tag tree
  • Haiku-as-fallback for ambiguous (~$30 total for 30k)
  • Cleanlab Datalab quarterly audit for label drift
→ multi-tier tagging at ~95%, ongoing cost ~zero
cost intuition Tagging 30k docs by handing every doc to an LLM: ~$300-$1500 (GPT-4 / Opus pricing) or ~$30 (Haiku). Cluster-then-propagate: ~$0 in API costs, just your time on the cluster labels. Hybrid (embedding-first, LLM-fallback): ~$30 with much higher quality than pure embedding.

08The simple, durable stack

For maintenance and longevity, the answer narrows hard. Three things matter: files as source of truth, index as regeneratable, tags inside the documents. Everything else flows from those.

file layout

corpus/                     # source of truth — markdown/txt, version with git
  memo-q4-2024.md           # yaml frontmatter for tags: [strategy, q4]
  slack-eng-2024-12-04.md   # one file per slack day or thread
  transcript-board.md       # one file per transcript

index.lance/                # LanceDB single-file store — REGENERATABLE
config.yaml                 # embedding model + chunking choices
search.py                   # ~150 lines — index() / search() / tag()

the pluggability contract

One property holds everything together: the index is regeneratable from the corpus. You can blow away index.lance/ at any time and rebuild from corpus/. That single property is what makes every layer swappable:

swap embedding model
change config.yaml, run reindex. Embeddings are durable data; the function that produced them is not.
swap vector store
read index.lance/ with DuckDB, write to Qdrant/Postgres/wherever. Lance format is open Arrow.
swap search frontend
CLI today, MCP server tomorrow, FastAPI + web app the day after. All wrap the same search.py module.
portable tags
yaml frontmatter inside each .md file. No tag DB. Edit in any text editor, version with git, query with rg.
durable embeddings
computed once, reused for years. Re-embedding is a 1-time hour-long batch when you upgrade the model.
layered tagging
v1: cluster & label. v2: add k-NN classifier. v3: LLM fallback. Each layer is optional and additive.

dependencies (4 of them)

  • lancedb — vector store
  • ollama Python client — local embedding service
  • pyyaml — config + frontmatter
  • click — CLI shell

All Apache 2.0 / MIT, all post-1.0, all maintained by orgs that aren't going anywhere. Add bertopic, cleanlab, modAL-python when you reach the tagging phases — those are bolts, not foundations.

10Exposing your corpus via MCP

The bridge from "I have a working search index" to "Claude Code / Cursor / any agent can query my corpus" is an MCP server. ~100 lines of Python in the minimal case. Below: what to expose, what to copy, what to skip.

tool surface — what to expose

reference servers worth reading

  • modelcontextprotocol/servers/memory — Anthropic's knowledge-graph memory server. Best for: how to model entity-relation observations.
  • filesystem — permission boundary pattern (`allowed_directories` env var). Copy this for sandboxing.
  • git — handles large result sets via streaming + structured snippets. Copy for paginating search hits.
  • vurtnec/mcp-LanceDB-node — LanceDB-specific MCP server. Most relevant reference for what we're building.
  • fetch — returns structured JSON (title/text/links) with `outputSchema`. Best example of typed responses.

schema design — what makes a tool the model actually calls

  • Flat input schemas. Don't nest. search(q, tag, after_date, limit) beats search({filters: {tag, dates: {start, end}}}).
  • Action-driven names. search_corpus > query. recent_docs > list_recent.
  • Use outputSchema (MCP 2025-06-18+). Strict JSON typing makes responses parseable without prompting.
  • Description = when to call. "Find documents semantically similar to a known document. Use when the user wants related reading." > "Returns related docs."
  • Return structured JSON, not markdown. Let the client format. Saves tokens, enables filtering downstream.

the minimal MCP server

from mcp.server import Server
import lancedb

server = Server("corpus-search")
db = lancedb.connect("./index.lance")

# minimum: search + get
@server.tool()
def search(query: str, limit: int = 5) -> list[dict]:
    """Search the personal corpus by semantic + keyword. Returns top hits with snippets."""
    hits = db.open_table("docs").search(query).limit(limit).to_list()
    return [{"id": h["id"], "score": h["_score"], "snippet": h["text"][:240]} for h in hits]

@server.tool()
def get(doc_id: str) -> dict:
    """Fetch the full content of a document by id."""
    return db.open_table("docs").search().where(f"id = '{doc_id}'").to_list()[0]

server.run()

Wire that into Claude Code's ~/.claude/mcp_servers.json and you're done. The agent can search and read your corpus. Skip pagination, auth, observability until you actually need them.

12Evaluating without labels

The personal-corpus problem: no golden query-doc pairs, can't run BEIR, can't compute MAP. So how do you know your search works?

the eval methods, in order of effort:value

  1. Diagnostic suite — write 20–30 hand-crafted "if my search can't answer this, it's broken" queries covering: edge cases, multi-hop, negation, date filters, rare entities. Manual. Irreplaceable.
  2. Synthetic queries — LLM generates 3–10 queries per sampled doc with varied prompts (short-keyword, short-verbose, long-verbose) to avoid overly-easy queries. Compute Recall@k, nDCG@5.
  3. LLM-as-judge — present (query, retrieved-doc) pairs to an LLM, ask "is this relevant?". Use binary, not 0–100. Run 3× per pair; measure judge agreement.
  4. RAGAS (ragas v1.2) — bundles synthetic queries + LLM-judge for faithfulness, context precision/recall, answer relevance. Still SOTA in 2026.
  5. eRAG (arXiv:2510.21440) — utility-based: score each doc by running RAG with only that doc as context. 50× lower GPU memory than full RAG eval. Higher Kendall's τ.
  6. Cluster coherence — for tagging, use silhouette + topic coherence (CV / NPMI). Aim for silhouette > 0.5, coherence > 0.65. Manual eyeball of top-5 words per cluster catches drift the metrics miss.
  7. Drift detection — log query → top-k weekly. KL/Jensen-Shannon divergence vs baseline. Flag > 0.1.
LLM-judge gotchas Numeric 0–100 scoring drifts; use binary. Single calls are noisy; run 3× and measure agreement. Calibrate by hand-labeling 50–100 examples and measuring TPR/TNR — then correct the judge's raw rates: actual_rate = TPR · predicted + (1 − TNR) · (1 − predicted).

the 1-day minimum harness

  • Generate 500 synthetic queries (5 per 100 sampled docs)
  • Run Recall@10 and nDCG@5 against your baseline embedding
  • Hand-write 25 diagnostic queries; manually label pass/fail
  • Compare 2–3 embedding models on diagnostics; pick winner
  • Wire weekly drift log: query, top-k, KL-divergence alert at p<0.05

~2-3 hours human time, $5-20 LLM API spend. Result: you'll know if search works and catch degradation. Don't build a full RAGAS harness until you have 10k+ monthly queries.

13From search to "knows me" — the personal memory frontier

Once search works, the next question is: should the agent remember things across sessions? The 2026 design space splits cleanly into three approaches with different bets about what humans + AI need to retain.

the three approaches

  • Personal RAG — retrieval over your own corpus. No learning, no consolidation. Fastest, dumbest, cheapest. What we've been building.
  • Memory layer (Mem0, Letta, Honcho, Zep) — service that manages memory lifecycle: write, retrieve, consolidate, expire. Tracks preferences, patterns, conflicts ("I changed my mind about X").
  • Fine-tuning — bake preferences into model parameters. Expensive to update, stale by inference time. Rarely worth it for personal use.

memory frameworks — the head-to-head

Why filesystem is winning for personal use: filesystems are observable. You can read your own memory. Cursor, Claude Code, and Cline all mount memory as directories because it maps to how developers already reason about state. Databases hide structure; files make it auditable. Plus, no network round-trip for retrieval.

the Tulving distinction matters

Episodic memory = "I failed the pipeline on March 3 because schema changed." Semantic memory = "this pipeline is fragile around migrations." Frontier work (CoALA) formalizes consolidation: how episodes become semantic patterns. For personal AI, episodic matters most — you want the agent to remember your specifics.

privacy Embeddings leak sensitive attributes via cosine similarity (arXiv:2504.15965 reports ~94% accuracy reconstructing medical diagnoses; ~69% attribute-level privacy violations from episodic memory). Application-layer encryption before sending to vector DB is the standard. Embeddings are not opaque.

the honest take for an audience of one

  1. Start with RAG + filesystem. Embed your corpus locally, mount agent memory as files. Fast, auditable, costs almost nothing.
  2. If you need preferences or learned patterns, add a memory layer (Claude Managed Agents on Anthropic API; Letta if open).
  3. Don't fine-tune unless you have 10k+ examples and a fixed domain.
  4. Don't build multi-source memory yet — the tooling isn't unified. Pull data on demand via APIs.

16Things to ignore

  • "Frameworks" — LlamaIndex, Haystack. Enterprise-shaped. Save more time than they cost only if you have ≥3 engineers.
  • Atlas, Pinecone, Weaviate Cloud — managed vector DBs. ~$50-500/mo for capacity you won't use at this scale.
  • Multi-vector retrieval (ColBERT v2) — mostly displaced by single-vector + hybrid + reranker. Storage cost ~10x. Skip unless you specifically need fine-grained scoring.
  • Pure long-context "stuff everything in" — RULER and Lost-in-the-Middle results show frontier models drop 30-50% past ~200k tokens. Your corpus is 50M.
  • Re-embedding every time the model changes — embeddings are durable. Pick a good one once, keep using it. Re-embedding is a 1-time hour-long batch when you upgrade.

17Open questions worth running experiments on

  • Does late chunking (Jina v3) actually beat naive chunking on your specific transcript style? Worth A/B-ing.
  • Is the hybrid retrieve → top-50 → 1M-context model pattern better than retrieve → top-5 → smaller model? Probably yes for hard questions, no for find-similar.
  • Does per-tier embedding fine-tuning (different small head per tag tier) outperform a single classifier? Cheap to test once Phase 2 is running.
  • Slack-message-as-doc vs slack-thread-as-doc — does retrieval quality depend on this granularity? Try both, measure.
