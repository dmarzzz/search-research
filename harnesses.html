02Hermes Agent — the deep dive

You asked about Hermes specifically. Here's what's actually shipping. github.com/nousresearch/hermes-agent · v0.13 "Tenacity Release" (May 7, 2026) · 140K stars · actively developed · Apache 2.0.

the agent loop

ReAct-derivative. A user turn becomes one agent invocation: assemble system prompt (frozen per session for cache reuse) → API call → parse reasoning + tool calls → execute all tools in parallel → collect → loop or conclude. The architecture optimizes for prompt stability (10× cost savings via cache) over turn-by-turn granularity. Skills are loaded in three tiers — summary → full → references-only — to avoid context bloat.

HRR memory — what it actually does

This is the architecturally novel piece. Hermes's Holographic memory provider stores memories as superposed complex-valued vectors in local SQLite. Memories compose algebraically via circular convolution, not by cosine similarity. In practice:

circular convolution as memory composition

storing
memory = user ⊛ prefers ⊛ async
+ user ⊛ role ⊛ writer
two facts superposed in one vector. ⊛ is binding (circular convolution).
querying — "what role?"
memory ⊘ (user ⊛ role)
≈ writer
unbinding by inverse convolution recovers the bound value. algebra, not similarity.

The win over vanilla embeddings: compositional queries. "Facts about user AND async" is one operation, not a two-step retrieve-then-filter. Trade-off: HRR is harder to reason about, requires NumPy at runtime (silently falls back to FTS5 if missing), and benefits scale with how compositional your queries are.

memory tiers + external providers

  • Built-in: MEMORY.md (sessions, FTS5-searchable) + USER.md (static profile)
  • External providers (8): Holographic (HRR), Honcho (cloud user modeling), Hindsight (knowledge graph + temporal), Supermemory (semantic + context fencing), and four more
  • Consolidation: on-demand only — skill_manage distills runs into reusable markdown runbooks. No automatic dreaming yet.

plugging in your MCP server

# ~/.hermes/config.yaml
mcp_servers:
  my_corpus:
    command: "python /Users/me/Galaxy/Grove/search/corpus-search/mcp_server.py"
    args: ["--port", "9999"]
    env:
      LANCEDB_PATH: "/Users/me/Galaxy/Grove/search/corpus-search/index.lance"
    tools:
      include: ["search", "get"]   # whitelist; blacklist via exclude

Tools auto-namespace as mcp_my_corpus_search. Runtime listChanged notifications mean you can hot-reload without restart. The model sees the tool description and decides when to call.

limitations & gotchas

  • 64K context floor — models with <64K rejected at startup; meta-cognition costs 10–50× the actual work on frontier models
  • HRR silently degrades — missing NumPy falls back to FTS5-only with no warning (v0.9.0–0.13)
  • 3B/8B models choke on deeply-nested tool schemas — needs 70B+ or frontier for planning
  • MCP namespace collisions — overlapping tool names across servers shadow silently. Use whitelists.
when to pick Hermes Need cross-session learning (skills built from past runs). Want HRR's compositional memory. Want a scheduled cron-driven agent that runs without you. Otherwise — Claude Code is the simpler path. Use both: Claude Code for active coding, Hermes for background workflows.

04MCP integration — what breaks at scale

The minimal MCP server is ~30 lines. It works. But once you wire it into a daily driver alongside other servers, the failure modes get specific.

the tool-bloat curve

The single most-cited 2026 finding from the field: tool selection accuracy collapses as MCP server count grows. From an 856-tool study and Atlassian's mcp-compressor work:

98%
5 servers preloaded
~2k tokens of tool descriptions in the system prompt. accuracy ~98%.
35%
15 servers preloaded
~12k tokens. accuracy collapses — the model picks wrong tool 7 times in 8.
91%
15 servers + tool search
~800 tokens (lazy-loaded definitions). accuracy recovers. Claude Code 2026 ships this.

Practical limit: 8–12 simultaneously-active MCP servers before degradation. Beyond that, lazy-load via tool search index, or aggressively whitelist.

the gotchas, ranked by how often they bite

Tool description drift
The model reads tool descriptions to decide whether to call. Underspecified descriptions cause it to pick wrong tool, supply invalid args, retry-loop. Update descriptions when behavior changes.
treat tool descriptions as part of the API surface; version them
LanceDB concurrent writes
Concurrent reads are safe (MVCC). Concurrent writes silently lose data after retry-limit exhaustion. If Claude Code AND Cursor both ingest, you'll lose updates.
single-writer pattern + advisory locks (fcntl)
Cost runaway
Agent calls search() 50× per turn with slightly-different wording. November 2025: 4-agent market research pipeline ran 11 days, $47k bill.
rate limit in server (10/min/session) + tool budget in harness + recent-query dedup
Stdio + stdout collision
Anything written to stdout breaks the JSON-RPC protocol. Logging library defaults to stdout. Server appears to crash with no useful error.
log to stderr always, or use MCP notifications/message
MCP version skew
2025-06-18 spec broke JSON-RPC batching. Old server + new client = malformed responses. 2025-11-25 added async tasks.
version-negotiate in Initialize; declare supported versions on both ends
Hardcoded tokens in config
~/.claude/mcp_servers.json committed with API key. The classic. Local-only stdio servers don't need auth (process boundary IS the auth).
env vars, never config; .gitignore the config dir

05Long-running loops & the daily-driver question

The honest answer: "personal AI as primary tool" is not yet a mainstream production pattern. The halfway-there versions are real and shipping. Here's the actual landscape.

the loop shapes

Conversational
sync, model in the loop
User types, agent responds, repeat. Default mode for Claude Code, Cursor, Cline. Best for active work — coding, writing, research.
fails when task takes longer than your attention; agent waits forever for input
Cron-driven
scheduled, async
Wake hourly/daily. Stateful cron ties schedule to a thread_id — every run appends to the same conversation. Hermes ships this natively.
fails when conversation history grows past usefulness — context drift over weeks
Event-driven
trigger on signal
File watcher, email arrival, calendar event, git push. Writer launched event-listener playbooks Nov 2025 — natural language, no code.
fails when the trigger fires on noise; agents respond to spam, churn through tokens
Autonomous loop
give it a goal
Agent picks its own next action. AutoGPT-style. Anthropic's "dreaming" + multi-agent orchestration pushes this further.
fails when the agent enters an unintended infinite loop — the $47k/11-day case is the warning shot

what successful setups actually look like (early 2026)

  • Karpathy's three-layer stack — tab completion (75% of work) + Claude Code for substantial chunks + ephemeral code for debugging. Plus an LLM Wiki: structured markdown files Obsidian can navigate, that Claude points at for complex questions. Smart home runs through "Dobby," a single WhatsApp agent. Moved from 80% human / 20% agent → 20% human / 80% agent in Dec 2025. writeup.
  • Simon Willison's setup — heavy on shell-script glue between Claude API and a local SQLite. Agentic Engineering Patterns + Pragmatic Summit talk (Mar 2026).
  • Anthropic's "dreaming" — Claude Managed Agents review past sessions, consolidate memory, surface patterns. The first time automatic consolidation shipped as a feature, not a paper. announcement · VentureBeat coverage.
  • Stateful cron — Vitalii Elenhaupt's Autobot ties cron to thread_id. Research agent builds on yesterday's findings. writeup.

the failure modes that bite

Context drift
Agent operates for months; context slowly goes stale. Accuracy degrades because the world changed, not because the model did. Documented but undermonitored.
consolidate weekly; let dreaming/manual journaling refresh facts
Hallucinated state
Inventory agent invents a nonexistent SKU, then calls four downstream APIs to price/stock/ship the phantom. One hallucination → multi-system incident.
read-after-write verification; require existing-id for actions
Cost runaway
November 2025: a 4-agent market research pipeline entered an unintended infinite loop. Ran for 11 days. $47,000 bill.
hard budget enforcement at the governance layer — terminate before ceiling, not at it
Stale memory
Facts in memory get out of date silently. "User prefers async" was true in March; now they don't. No mechanism flags it.
version memories with valid_at; use Zep-style temporal graphs if this is your bottleneck

the trust gradient

Anthropic's research on Claude Code: newer users grant full auto-approve ~20% of the time. By 750 sessions, that jumps to over 40%. Trust compounds with experience. Email, calendar, code-push still require explicit approval in all shipping systems as of May 2026.

06The recommended path forward

For someone who has the corpus + index + simple stack from Part I, the highest-leverage next moves:

  1. Build the minimal MCP server (§10 of Part I). 30 lines. Wire into ~/.claude/mcp_servers.json. This alone gets you 80% of the value.
  2. Use Claude Code as your daily driver. Plaintext state, predictable loop, MCP first-class. Don't fight the tooling.
  3. Add a cron-driven loop for one specific task (e.g., "every Monday at 9am, summarize last week's slack into a digest"). Don't try to make the agent autonomous — just scheduled.
  4. Layer in dreaming-style consolidation when memory growth becomes painful. Could be a manual weekly review, or — if you're on Anthropic's API — Claude Managed Agents with their dreaming feature.
  5. Don't pursue full autonomy. The trust gradient says it's not where you should aim. Aim for "helpful background runner" not "fully autonomous agent." The cost runaway risk is real.
honest take None of this is the future. It's just the 2026 best-of-shipping. Karpathy is an optimist; the median knowledge worker still has a fragmented stack — Claude for writing, Perplexity for search, Granola for meetings, plus five other tools. Integrated personal AI is real but rare. Build for the halfway-there pattern; don't wait for the unified agent.

07What's not yet possible

  • True multi-source memory — fusing Slack + email + transcripts + calendar into one coherent personal memory. Pieces exist (Honcho, Mem0, Letta), but no production framework does it elegantly. DIY is still the frontier.
  • Agent-to-agent memory sharing — two harnesses (Claude Code + Hermes) reading the same memory store. The MCP server pattern could do this but no one's polished it.
  • Cross-device personal memory — laptop, phone, watch, all sharing one memory. The privacy story isn't there yet (embeddings leak ~94% reconstruction of sensitive attributes per arXiv:2504.15965).
  • Reliable autonomy beyond ~30 minutes — agents that run unsupervised for hours and don't drift, hallucinate, or run up bills. Anthropic's measuring-agent-autonomy work confirms this is the open frontier.
  • "Plug-in" personal AI — drop a folder of your data, get a daily-driver. Khoj and Reor are closest. Still rough.

08Open questions worth experimenting with

  • Does HRR's compositional memory actually outperform vanilla cosine retrieval for your query patterns? Worth A/B-ing if you choose Hermes.
  • How many MCP servers can you connect before tool-selection accuracy drops? Run the experiment with 5, 10, 15. Lazy-loading saves you, but at what cost.
  • Stateful cron + same thread_id over weeks: does context drift kill it? Or does dreaming-style consolidation rescue it?
  • For multi-agent setups, is single-writer + many-readers actually robust enough? Or do you need a coordination layer?
  • Trust-gradient experiment on yourself: can you get to 60% auto-approve in 90 days, or does friction win?
