The production frontier

Part III. Four open questions at the edge of personal-AI in early 2026: how do you actually measure value, what's the math under HRR memory, does dreaming-style consolidation work, and is multi-agent real or marketing?

scope: open frontier focus: production reality compiled: —
if you only read one thing Karpathy's "80% agent" claim is vibes. METR's reproducible RCT found AI made experienced devs 19% slower while they felt 20% faster. HRR is real but niche — it wins on compositional queries, loses on general retrieval. Dreaming works (Anthropic ships it; Harvey reports 6× completion gains) but is premature optimization under ~20 sessions/week. Multi-agent is mostly hype — 41-86% of multi-agent systems fail; supervisor-worker dominates the rest; for one user, one smart agent + 20 tools beats 20 agents.

01How prosumers actually measure agent value

The Karpathy claim, dissected. Most "I'm 80% agent now" claims are self-reported workflow vibes — credible because of who said them, but not measurable. The actual data is more interesting and less flattering.

the four numbers that matter

+19%
METR study (Jul 2025)

~0%

26K commits analyzed pre/post Copilot. No statistically significant change in commit activity.

20→40%
Trust gradient
Anthropic data: auto-approve rate climbs from ~20% (50 sessions) to ~40% (750 sessions). The one reproducible objective metric.

The pattern: AI feels productive even when it isn't. Output works but fails code review (missing tests, lint, quality standards) — the cleanup tax doesn't show up in benchmarks. Real-world devs end up doing roughly the same work, but rate the experience higher.

honest take Karpathy's 80/20 is aspirational vibes. METR's slowdown is reproducible. The gap between subjective speed and objective speed is real and persistent. Don't let prestige names override published data.

the minimum reasonable measurement setup

  1. Cost telemetry. Anthropic Console / OpenAI dashboard / Helicone / Langfuse. Free tier handles 10K-50K events. Watch monthly spend trend; serious daily-driver use lands $30-200/mo.
  2. Auto-approve trend. Count permission prompts per session, plot over 4 weeks. Climbing = building trust or getting predictable. Flat or declining = something broke.
  3. 4-week on/off cycles. Pick one recurring task. 2 weeks no agent (baseline) → 2 weeks with. Log time + cost + 1-5 quality rating. Confounds abound but qualitative differences reveal themselves.
  4. Friday smoke test. Every Friday, run 5-10 tasks the same way. Compare to week 1. Drift detection without infrastructure.

~2 hours of setup. ~10 min/week ongoing. Result: you'll know if your agent is silently underperforming, before $47k worth of inference burn.

02HRR — the math, and when it actually wins

You saw the surface algebra in Part II. Here's the real math beneath, and the honest answer to "should I use this." Tony Plate's 1995 paper (PDF) is foundational and still readable.

the binding/unbinding mechanic, formalized

circular convolution + correlation = bind + unbind

binding
a ⊛ b = F⁻¹(F(a) ⊙ F(b))
F = FFT, ⊙ = element-wise product. O(d log d) via FFT vs O(d²) direct.
unbinding
(a ⊛ b) ⊘ a ≈ b
⊘ is circular correlation (approximate inverse). Lossy — recovers b plus noise proportional to memory load.
superposition
memory = a₁ ⊛ b₁ + a₂ ⊛ b₂ + ... + aₙ ⊛ bₙ
All facts summed into one fixed-width vector. Capacity ~O(d/k) for d-dim vectors and k-dim per binding.

HRR vs HDC (Kanerva)

The other family of vector-symbolic architectures, from Pentti Kanerva's 2009 work. Same goal, different mechanics:

when HRR wins Knowledge-graph-shaped queries: "what role does X play?", "facts about X AND Y". Local-only / private (no API). Less than ~10k facts. HRR is production-ready but niche. 2026 production agents converge on hybrid: vector + episodic + graph, with HRR as the vector layer when compositional retrieval matters.

capacity: what breaks at scale

Plate's analysis: a d-dim vector cleanly stores ~O(d/k) bound pairs before signal-to-noise degrades. For d=1024 (Hermes default), that's 40-100 facts. For d=4096, ~250. For d=10,000, ~1000. After that, unbinding returns superpositions of multiple values — the model has to disambiguate.

The 2026 papers (Kleyko et al. survey) show that learned binding (Schlegel NeurIPS 2021) closes some of this gap by training the binding op end-to-end with the rest of the model. Niche; not in Hermes yet.

03Memory consolidation / "dreaming" — the frontier

Anthropic shipped this in May 2026 as a research-preview. The interesting part: the algorithm is not novel. It's just scheduled LLM-as-judge over your transcripts. The novelty is shipping it as a feature instead of leaving it as a paper.

what dreaming actually does

the consolidation algorithm — reverse-engineered

  1. Retrieve N most recent sessions (or all since last consolidation)
  2. Extract salient facts: repeated patterns, mistakes, learnings, preferences. LLM call.
  3. Cluster or match new facts against existing long-term memory (embedding similarity OR LLM judgment)
  4. Merge: UPDATE contradictions, DELETE stale entries, ADD novel insights
  5. Score candidates: relevance · frequency · recency · consolidation-readiness (weighted ranking)
  6. Write consolidated notes and playbooks back to persistent store

That's it. No new math. The leverage is in scheduling (offload to off-peak compute), incremental updates (don't re-process everything), and auditability (consolidated notes are inspectable plain text).

the four shipping consolidation patterns

Anthropic dreaming
Scheduled review of full transcripts. Writes plain-text notes + playbooks. Harvey reports 6× completion-rate improvement post-rollout. announcement
→ best if you're on Anthropic's API stack
Letta sleep-time subagents
Background reflection rewrites memory blocks. Off-peak compute. User can also /remember to trigger manually. repo
→ best for self-hosted on Postgres
Mem0 incremental clustering
New facts matched against top-K existing memories via embeddings + LLM judgment. ADD/UPDATE/DELETE/NOOP per pair. Real-time, not batched. repo
→ best when consolidation must be live
Honcho async reasoning
Background dreaming agent crawls user data, fills gaps, forms hypotheses. Peer cards + abductive inference. Plastic Labs' bet. repo
→ best for cross-platform user modeling

04Multi-agent — reality check

A2A is real. Frameworks exist. But the production data is harsh: 41-86% of multi-agent systems fail, mostly from poor task decomposition and missing termination conditions. And they cost 3-5× the tokens of equivalent single-agent setups.

the protocol stack, sorted

  • MCP (Model Context Protocol) — agent-to-tool. Anthropic-led, governed by Linux Foundation AAIF since Dec 2025.
  • A2A (Agent2Agent Protocol) — agent-to-agent. Google-led, 150 production deployments first year (Netflix, Harvey, Salesforce, AWS, Microsoft). JSON Agent Cards for capability discovery, SSE for streaming.
  • ACP (Agent Communication Protocol) — IBM's. Merged into A2A August 2025. Don't track separately.

MCP and A2A are complementary, not competing. Both governed by the same foundation. Most personal-AI builders don't need to think about A2A yet — it matters when crossing organizational/vendor boundaries.

orchestration patterns — what works

Supervisor-worker
One orchestrator decomposes tasks, routes to specialists, recombines. ~70% of production deployments. Boring; works.
→ if you must have multi-agent, this is the shape
Swarm / mesh
Peer-to-peer, no coordinator. Theoretically elegant. Rarely outperforms hierarchy in practice. Most "swarm" deployments are supervisor-worker in disguise.
→ academic interest only
Pipeline (A → B → C)
Linear hand-off. Works for fundamentally sequential workflows (ingest → enrich → write). Single agent + tools usually does this better.
→ probably should be one agent
Critic / judge
One agent generates, another evaluates. Useful for self-correction loops. Anthropic's Constitutional AI pattern.
→ niche but legitimate

honest take For one user with one personal corpus and one MCP search server: do not add a second agent. "Research agent + writing agent + scheduler" sounds elegant. In practice, one smart agent with research tools, writing templates, and calendar access does 80% of the work at 20% the complexity. Add the second agent only when the first is bottlenecked on something it's measurably bad at — not speculatively.

05The recommended path through this

Putting Parts I, II, and III together — what to actually do with all this:

  1. Build the simple stack (Part I §08): corpus/ + index.lance/ + config.yaml + search.py. ~1 weekend.
  2. Wire up minimal MCP server (Part I §10 + Part II §04): ~30 lines of Python. Connect to Claude Code via ~/.claude/mcp_servers.json.
  3. Use it as a daily driver for 2 weeks with no eval. Just use it. Get a feel.
  4. Then set up minimal measurement (Part III §01): cost telemetry + auto-approve trend log + Friday smoke test. ~2 hours setup.
  5. Add ONE cron-driven task (Part II §05): something specific and verifiable, like a weekly slack digest.
  6. Don't add multi-agent until you have a single workflow you can prove benefits from it. Most don't.
  7. Add dreaming only if memory growth becomes painful (~20+ sessions/week). Below that threshold, it's premature.
  8. HRR-backed memory is interesting but optional. Stick with vanilla embeddings unless you specifically need compositional queries.

06What's next at the frontier

Genuinely open questions as of May 2026 — places where the answers haven't shipped yet:

  • Reliable autonomy beyond ~30 minutes. The $47k/11-day cost runaway is the warning shot. Nobody has shipped a confidently-autonomous agent that runs for hours unsupervised without drift, hallucination, or budget overruns.
  • True multi-source personal memory. Slack + email + transcripts + calendar fused into one coherent memory. Pieces exist (Honcho, Mem0, Letta). No production framework does it elegantly.
  • Cross-device personal memory. Laptop + phone + watch sharing one memory, with privacy. Embeddings leak ~94% reconstruction of sensitive attributes (arXiv:2504.15965). The tooling isn't there.
  • Personal-scale objective productivity. METR's slowdown finding hasn't been refuted. The way forward might be picking workflows where AI clearly wins (boilerplate, debugging, refactor-at-scale) and avoiding ones where it doesn't (architectural decisions, novel research).
  • HRR + learned binding. Schlegel et al. showed end-to-end learned binding works. No production agent has shipped it yet. The first to do so might unlock genuinely compositional agent memory.
